# Contratos de la telemetría vehicular

## Alcance y límites

U1 (`u1-telemetry-core`) publica los contratos de la única Lambda `TelemetryService`. U2 amplía esa Lambda y consume sus modelos; U3 empaqueta y despliega el mismo artefacto. API Gateway REST invoca la Lambda para HTTP y EventBridge invoca **esa misma Lambda** para recuperar salidas pendientes. DynamoDB contiene dos tablas, evento y Outbox; SQS se usa únicamente para alertas. No existe mensaje ni DLQ de ingreso.

| # | Provider Unit | Consumer | Mechanism | Owner |
|---|---|---|---|---|
| C1 | U1 | External: productores de telemetría | REST/HTTP `POST /telemetry-events` | U1 |
| C2 | U1 | External: consumidor de alertas | Mensaje JSON en SQS de alertas | U1 |
| C3 | U1 | U2 | Esquema compartido de evento y Outbox dentro del mismo servicio | U1 |
| C4 | U1 | U3 | Manifiesto de artefacto, CDK y prueba crítica | U1 |
| C5 | External: regla EventBridge | U1 | Evento programado a la misma Lambda | U1 |

## C1 — API HTTP de ingestión

`202` significa que se confirmó el evento y, para batería estrictamente menor que 20, una salida Outbox `PENDING` en **una transacción**. No acredita recepción de la alerta. La publicación SQS puede fallar después sin revocar la aceptación. Un duplicado exacto devuelve `202` con `acceptedAt` y `correlationId` originales, sin reescritura ni nueva publicación causada por el reenvío. Se comparan los cinco campos contractuales (`eventId`, `vehicleId`, `eventType`, `timestamp`, `value`) tras normalizar el instante UTC y el valor numérico. Reutilizar `eventId` con contenido distinto devuelve `409 IDEMPOTENCY_CONFLICT` y conserva el primer evento. El encabezado de correlación no forma parte de esa comparación.

La validación falla antes de cualquier escritura: identificadores de 1–128 caracteres ASCII `[A-Za-z0-9._:-]`, instante ISO 8601 UTC no posterior a cinco minutos en el futuro, número finito y rangos por tipo. `X-Correlation-Id` usa el mismo patrón; si falta, la Lambda genera uno. Los errores generados por Lambda usan `code`, `message`, `correlationId`. Los rechazos de clave, cuota o limitación se originan en API Gateway, antes de Lambda, y su cuerpo puede diferir. El plan por clave configura 100 solicitudes/s, ráfaga 200 y cuota diaria 5.000.000; AWS aplica estos objetivos de manera aproximada [1]. El cliente puede reintentar un fallo transitorio con el **mismo** `eventId`, con retroceso exponencial; no debe cambiar el contenido del evento.

La clave `eventId` es global entre vehículos **mientras exista el registro**. `expiresAt` lo hace elegible para borrado a los 90 días y, tras su eliminación física, el servicio ya no puede garantizar la detección de una reutilización. El productor debe generar IDs que nunca reutilice. Esta acotación se deduce de FR4.2 y NFR4; la pregunta opcional de aclaración no recibió respuesta.

```yaml
openapi: 3.0.3
info:
  title: Vehicle Telemetry Ingestion API
  version: 1.0.0
paths:
  /telemetry-events:
    post:
      operationId: acceptTelemetryEvent
      summary: Validate and durably accept one telemetry event
      security:
        - ApiKeyAuth: []
      parameters:
        - name: X-Correlation-Id
          in: header
          required: false
          schema:
            $ref: '#/components/schemas/Identifier'
          description: Generated by the service when absent.
      requestBody:
        required: true
        content:
          application/json:
            schema:
              $ref: '#/components/schemas/TelemetryRequest'
      responses:
        '202':
          description: Transaction committed, or exact duplicate of an already committed event. Alert delivery is not implied.
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Accepted'
        '400':
          description: Invalid JSON, required field, identifier, timestamp, type or value. No side effects.
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/LambdaError'
        '409':
          description: eventId already committed with different contractual content; code IDEMPOTENCY_CONFLICT.
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/LambdaError'
        '503':
          description: Persistence temporarily unavailable or commit result cannot be confirmed; never represents acceptance.
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/LambdaError'
        '500':
          description: Unexpected Lambda failure; never represents acceptance.
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/LambdaError'
        '403':
          description: API Gateway rejects absent or invalid API key before Lambda; gateway-generated body.
        '429':
          description: API Gateway throttling or quota response; gateway-generated body.
components:
  securitySchemes:
    ApiKeyAuth:
      type: apiKey
      in: header
      name: x-api-key
  schemas:
    Identifier:
      type: string
      minLength: 1
      maxLength: 128
      pattern: '^[A-Za-z0-9._:-]+$'
    TelemetryRequest:
      type: object
      additionalProperties: false
      required: [eventId, vehicleId, eventType, timestamp, value]
      properties:
        eventId:
          $ref: '#/components/schemas/Identifier'
        vehicleId:
          $ref: '#/components/schemas/Identifier'
        eventType:
          type: string
          enum: [battery, temperature, speed]
        timestamp:
          type: string
          format: date-time
          description: ISO 8601 UTC instant, no more than five minutes after service time.
        value:
          type: number
          description: Finite; battery 0..100 %, temperature -50..150 C, speed 0..300 km/h.
    Accepted:
      type: object
      additionalProperties: false
      required: [status, eventId, acceptedAt, correlationId]
      properties:
        status:
          type: string
          enum: [accepted]
        eventId:
          $ref: '#/components/schemas/Identifier'
        acceptedAt:
          type: string
          format: date-time
          description: Original UTC acceptance instant at second granularity; unchanged on an exact duplicate.
        correlationId:
          $ref: '#/components/schemas/Identifier'
    LambdaError:
      type: object
      additionalProperties: false
      required: [code, message, correlationId]
      properties:
        code:
          type: string
          enum: [VALIDATION_ERROR, IDEMPOTENCY_CONFLICT, PERSISTENCE_UNAVAILABLE, INTERNAL_ERROR]
        message:
          type: string
        correlationId:
          $ref: '#/components/schemas/Identifier'
```

El contrato de error `503` incluye resultados de transacción inciertos: el productor reintenta con el mismo `eventId`; si la escritura sí se confirmó, el reintento obtiene el `202` original. Un `400` o `409` no produce efectos. La publicación de SQS queda fuera del camino que determina `202`.

## C2 — Mensaje de alerta SQS

Solo `eventType: battery` con `value < 20` genera una salida. `alertId` se deriva exactamente como `LOW_BATTERY:` seguido del `eventId`, por lo que es estable e inyectivo para este tipo de alerta. El cuerpo contiene los seis campos obligatorios siguientes; `occurredAt` es el `timestamp` normalizado del evento. La correlación viaja como atributo SQS `correlationId`. La entrega física puede repetirse por reintentos o reentrega de SQS: el consumidor aplica su efecto una sola vez por `alertId`. Un consumidor futuro debe ignorar campos desconocidos y no depender del orden de mensajes.

```yaml
asyncapi: 2.6.0
info:
  title: Vehicle Battery Alerts
  version: 1.0.0
channels:
  battery-alerts:
    description: Outgoing SQS queue; no inbound telemetry queue.
    publish:
      operationId: publishLowBatteryAlert
      message:
        $ref: '#/components/messages/LowBatteryAlert'
components:
  messages:
    LowBatteryAlert:
      name: LowBatteryAlert
      contentType: application/json
      headers:
        type: object
        required: [correlationId]
        properties:
          correlationId:
            type: string
            minLength: 1
            maxLength: 128
            pattern: '^[A-Za-z0-9._:-]+$'
      payload:
        type: object
        required: [alertId, eventId, vehicleId, alertType, batteryValue, occurredAt]
        properties:
          alertId:
            type: string
            maxLength: 140
            pattern: '^LOW_BATTERY:[A-Za-z0-9._:-]{1,128}$'
          eventId:
            type: string
            minLength: 1
            maxLength: 128
            pattern: '^[A-Za-z0-9._:-]+$'
          vehicleId:
            type: string
            minLength: 1
            maxLength: 128
            pattern: '^[A-Za-z0-9._:-]+$'
          alertType:
            type: string
            const: LOW_BATTERY
          batteryValue:
            type: number
            minimum: 0
            exclusiveMaximum: 20
          occurredAt:
            type: string
            format: date-time
            description: UTC timestamp of the originating telemetry event.
```

El Outbox conserva `PENDING` ante fallo o resultado incierto; se marca `PUBLISHED` solo tras confirmación SQS y actualización condicional. Si se confirma SQS y falla la actualización, se puede repetir el envío con el mismo `alertId`. La política de reintento, visibilidad y alarmas se fija en Infrastructure Design; el contrato externo no promete entrega exactamente una vez.

## C3 — Esquema compartido U1 → U2

U1 posee ambas entidades y sus invariantes; U2 añade validación, observabilidad y procedimientos operativos sobre el mismo código y las mismas tablas. `eventId` es clave global mientras el evento exista. El evento y la salida se crean juntos mediante una transacción condicional. `acceptedAt` se fija con precisión de segundos; `expiresAt` es un número de segundos Unix para TTL, calculado exactamente desde `acceptedAt + 90 días`; la eliminación física es eventual [2]. `nextAttemptAt` y la reclamación condicional permiten que la invocación programada recupere salidas vencidas sin cambiar `alertId`.

```yaml
shared-schema: 1.0
owner: u1-telemetry-core
consumer: u2-telemetry-operations
entities:
  TelemetryEvent:
    table: telemetry-events
    key: eventId
    required:
      eventId: Identifier
      vehicleId: Identifier
      eventType: battery|temperature|speed
      timestamp: ISO8601-UTC
      value: finite-number
      acceptedAt: ISO8601-UTC
      correlationId: Identifier
      expiresAt: unix-epoch-seconds
    invariants:
      - eventId is globally unique and immutable.
      - expiresAt equals acceptedAt plus 90 days at second granularity.
      - the five request fields determine duplicate versus conflict.
  OutboxEntry:
    table: telemetry-outbox
    key: alertId
    required:
      alertId: 'LOW_BATTERY:{eventId}'
      eventId: Identifier
      alertType: LOW_BATTERY
      batteryValue: number-below-20
      occurredAt: ISO8601-UTC
      status: PENDING|PUBLISHED
      nextAttemptAt: ISO8601-UTC
      attempts: nonnegative-integer
      createdAt: ISO8601-UTC
    optional:
      lastAttemptAt: ISO8601-UTC
    invariants:
      - created in the same transaction as its TelemetryEvent.
      - PUBLISHED only after confirmed SQS send and conditional update.
      - uncertain sends retain PENDING and the same alertId.
```

La estrategia de índices, arrendamiento/reclamación, tiempo entre intentos y campos internos adicionales queda para diseño funcional e infraestructura; no altera este esquema obligatorio.

## C4 — Artefacto y controles U1 → U3

U1 entrega un único artefacto Lambda, su pila CDK y la prueba integrada del recorrido HTTP y recuperación EventBridge. U3 usa ese artefacto para configurar CI, roles temporales OIDC, CloudTrail y promoción. La fusión a `main` despliega a `staging`; producción requiere aprobación manual. Ninguna variación de U3 puede incorporar una Lambda, SQS o DLQ de ingreso.

```yaml
shared-schema: 1.0
owner: u1-telemetry-core
consumer: u3-delivery-controls
handoff:
  application: one TelemetryService Lambda artifact
  infrastructure: TypeScript AWS CDK stack
  resources:
    - REST API Gateway endpoint POST /telemetry-events
    - one TelemetryService Lambda with HTTP and scheduled entry points
    - DynamoDB TelemetryEvent table with TTL
    - DynamoDB OutboxEntry table
    - SQS battery alerts queue
    - EventBridge recovery rule
  requiredVerification:
    - invalid HTTP request leaves both tables and SQS unchanged
    - valid request commits event and applicable PENDING outbox before 202
    - battery value 20 produces no alert; value below 20 does
    - scheduled invocation retries PENDING with the same alertId
  delivery:
    ci: [prettier, eslint, types, unit-tests, simulated-AWS-integration, dependency-scan, secret-scan]
    awsCredentials: temporary-OIDC-roles
    staging: deploy-on-main-merge
    production: manual-approval-required
    audit: KMS-protected-CloudTrail
```

## C5 — Activación de recuperación EventBridge → U1

La regla programada invoca la **misma Lambda** con un evento distinguible del proxy HTTP. La Lambda consulta salidas `PENDING` vencidas, las reclama de manera condicional y limita el trabajo por invocación. El formato de AWS del evento es responsabilidad del adaptador; U1 discrimina por `source` y `detail-type`, sin aceptar un evento programado como solicitud HTTP. Infraestructura fija frecuencia, permisos, límites de lote y concurrencia.

```yaml
shared-schema: 1.0
owner: u1-telemetry-core
producer: EventBridge-scheduled-rule
consumer: TelemetryService-Lambda
trigger:
  source: aws.events
  detail-type: Scheduled Event
  invocation: asynchronous
behaviour:
  - process only due PENDING OutboxEntry records
  - claim each record conditionally before publishing
  - preserve alertId across retries
  - keep PENDING when SQS outcome is failure or unknown
```

## Contract Ownership Rules

- U1 mantiene C1–C5 y publica cualquier revisión de sus esquemas antes de que U2 y U3 la consuman. U2 y U3 validan sus cambios contra esos contratos y no modifican la propiedad de las entidades.
- En v1, los cambios compatibles añaden solo campos opcionales, sin alterar el significado de los obligatorios, el umbral, la idempotencia o `alertId`. Los consumidores SQS ignoran campos desconocidos. El esquema HTTP se amplía de forma explícita cuando se introduzca un campo nuevo.
- Cambiar campos obligatorios, rutas, semántica de respuesta o identidad de alerta exige una nueva versión y adopción coordinada con los consumidores; U3 comprueba en CI la versión y las pruebas de integración antes de desplegar.
- Los contratos C3–C5 son internos del único servicio y su empaquetado; no autorizan despliegues separados de nuevas Lambdas ni lectura/escritura compartida por otro propietario.
